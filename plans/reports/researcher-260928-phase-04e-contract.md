# Phase 04E Contract Research — Delete Article

**Conducted:** 2026-09-28
**Scope:** `DELETE /api/articles/:slug`; repository contract and implementation conventions only.
**Preflight:** The `Skill` activation tool was not exposed in this session. I read the local `tkm:help` and `tkm:research` skill files directly before inspecting project sources. No external technology or library research was needed.

## Finding

Implement the route with required `Authorization: Token <jwt>`, a required slug path segment, and no request body. A valid owner request returns `204` with no response body. A valid-token request for an unknown slug returns `404 { errors: { article: ["not found"] } }`. Use the strict `AuthTokenGuard` convention, including `401` token envelopes.

OpenAPI lists `403`, so a forbidden case is part of the declared status contract. The sources do not explicitly say that a non-owner triggers it, nor define the resource key for that response. Owner-only deletion with `errors.article: ["forbidden"]` is the strongest local inference from the adjacent update API; label it as a local policy if adopted. Do not claim Hurl proves it.

## Persistence effects and fit

- The existing article schema has no soft-delete column; article identity is its unique slug. The established schema is a natural fit for a physical delete by slug. **Evidence:** Article entity fields and timestamps ([article.entity.ts:13-47](../../src/articles/article.entity.ts#L13)); 4A describes `slug` as unique and the article table shape ([phase-04a:25-30](../260910-0930-medium-clone-backend/phase-04a-article-schema.md#L25)); Hurl requires subsequent detail lookup to report not found ([articles.hurl:252-256](../../spec/api/hurl/articles.hurl#L252)).
- Deleting an article cascades its `article_tags` and `article_favorites` join rows at the database level. It does not imply deleting shared `tags`; 4A explicitly leaves unused tag-row cleanup for the later relevant API policy. **Evidence:** migration foreign keys use `ON DELETE CASCADE` ([1710000004000-create-articles-tags-favorites.ts:14-36](../../src/database/migrations/1710000004000-create-articles-tags-favorites.ts#L14)); entity relations agree ([article-tag.entity.ts:36-47](../../src/articles/article-tag.entity.ts#L36), [article-favorite.entity.ts:22-34](../../src/articles/article-favorite.entity.ts#L22)); 4A says unused tag rows are retained pending a later decision ([phase-04a:77-81](../260910-0930-medium-clone-backend/phase-04a-article-schema.md#L77)).
- The current article boundary is `ArticlesController` → service; the module already registers article, favorite, and tag metadata. Add the delete endpoint there and keep the controller at the HTTP boundary, following the same strict guard and typed-error mapping pattern used by create/update. **Evidence:** current controller routes and mappings ([articles.controller.ts:55-62,87-118,121-155](../../src/articles/articles.controller.ts#L55)); current strict guard ([auth-token.guard.ts:18-43](../../src/auth/auth-token.guard.ts#L18)); module providers/entities ([articles.module.ts:16-35](../../src/articles/articles.module.ts#L16)).
- No migration is indicated by the current schema: article deletion and dependent join cleanup are already modeled. **Evidence:** 4D notes the schema supports current operations without migration ([phase-04d:11-13](../260910-0930-medium-clone-backend/phase-04d-update-article.md#L11)); article and dependent foreign keys are in 4A's migration ([migration:14-36](../../src/database/migrations/1710000004000-create-articles-tags-favorites.ts#L14)); 4A already records the tables and delete cascades ([phase-04a:25-32](../260910-0930-medium-clone-backend/phase-04a-article-schema.md#L25)).

## Reconciliation and ranked implementation direction

1. **Follow executable Hurl for successful and missing-resource behavior:** strict Token auth, `204` empty response, then article-specific 404. Hurl is the strongest source for observable HTTP behavior; OpenAPI corroborates the status, and 4C/4D establish the local article error-envelope convention.
2. **Use the existing strict guard:** it is already used by authenticated create/update and produces `is missing` / `is invalid`. The invalid-token case is a codebase convention, not a DELETE-specific Hurl assertion.
3. **Resolve OpenAPI's generic errors at the operation boundary:** `NotFound` and `Forbidden` shared examples say `resource`, while article Hurl and adjacent article routes use `article`. Document article-specific 404. For the declared 403, owner-only + article-specific forbidden best matches PUT, but remains a local inference until a deletion-specific behavior is formally captured.
4. **Do not manufacture a 422 trigger.** Keep the existing generic OpenAPI status only if project-wide documentation conventions require it; do not add slug constraints or a body.
5. **Hard delete article only; rely on database cascades for article-tag/favorite rows; retain shared tag rows.** No migration is needed.
